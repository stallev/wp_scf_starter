# Производительность: решения и почему

Почему механизмы темы устроены именно так и что их ломает. Уровни: **P1** — встроено в код, **P2** — статический gate (e2e `perf-markup`), **P3** — PSI после деплоя ([`psi.md`](psi.md)). Реализация — [`contracts/theme.md`](../contracts/theme.md), [`contracts/images.md`](../contracts/images.md), [`analytics.md`](analytics.md). Цифры ниже — обезличенные кейсы исходного проекта.

Итоговый кейс: мобильный Performance 72–88 → 99–100, CLS 0 на всех шаблонах. Основной вклад — шрифты с fallback-метриками, снятие `.reveal` с LCP, одна LCP-картинка `eager + high`, отложенный GA4, фасад карты.

## Принципы

1. **Сначала измерить, потом чинить.** Каждое решение опирается на конкретный аудит (`lcp-breakdown-insight`, `cls-culprits-insight`, `render-blocking-insight`). «На всякий случай» — не причина.
2. **Первый экран важнее всего.** LCP, FCP, CLS определяет только видимое без скролла; всё ниже откладывается (`lazy`, `.reveal`, клик-до-загрузки).
3. **Не грузить то, чего пользователь не просил:** сторонний скрипт, карту, картинки ниже сгиба.
4. **Резервировать место заранее:** `width`/`height`, `aspect-ratio`, fallback-шрифт с подогнанными метриками.
5. **Одно значение — одно место** (конфиг / код), документ хранит только «почему».

## 1. Шрифты

| Решение | Почему |
|---|---|
| Локальные **variable woff2** по подмножествам (`unicode-range`), `font-display: swap`, `@font-face` в начале `main.css` | Один файл на подмножество вместо файла на вес; браузер сам берёт нужные подмножества; нет второго блокирующего CSS |
| Только woff2 | `.woff` вдвое тяжелее и без подмножеств |
| Preload только 2–4 файлов первого экрана (`fonts.preload`), всегда `crossorigin` (K5) | Файлы грузятся параллельно с CSS; без `crossorigin` preload скачивается дважды; preload всей семьи конкурирует с CSS и LCP |
| Fallback-face с `size-adjust` / `ascent-override` / `descent-override` / `line-gap-override` | Пока шрифт грузится, текст занимает столько же места — CLS от подмены → 0 |
| Без Google Fonts и чужих CDN (`check:naming`: `external-font-cdn`) | Лишний origin и блокирующий CSS |

**Метрики fallback — только измеренные по реальному тексту** (K4): `npm run fonts:fallback -- --font=<woff2> --family="Name"` рендерит текст сайта в Chromium и сравнивает ширины. Кейс: расчёт по метрикам файла дал 105 % вместо измеренных ~101.3 %, и значение различалось по весам. Пересчитывать при смене шрифта, подмножеств или основных весов. Кейс: подмена шрифта без fallback давала CLS 0.22 (mobile) и 0.46 (desktop).

## 2. Render-blocking CSS и JS

- Один `main.css` — единственный блокирующий стиль. Критический CSS сознательно **не** выносится: выигрыш ≤ 300 мс, а разбиение рискует сломать общие компоненты и порядок каскада (утилиты `is-hidden` последними). Если возвращаться к задаче: правила первого экрана — кейс ≈ 15–16 КБ; выносить поэтапно, проверять на каждом шаблоне, учитывать скрытые связи (классы подвала на всех страницах, порядок утилит).
- Каждый скрипт — `strategy => defer` (`starter_script_args()`). **Ловушка WP** (K2): если у скрипта есть зависимый без своей `strategy`, WordPress делает родителя блокирующим. Кейс: `gtag.js` стал parser-blocking с `data-wp-strategy="async"` без атрибута `async`, render-blocking ~1.8 с. Зависимости проверять по итоговому HTML (`perf-markup`).
- `defer`-скрипт выполняется до `DOMContentLoaded`, поэтому данные через `wp_add_inline_script( …, 'before' )` доступны; inline `<script>` и `on*=` в шаблонах нет.

## 3. `.reveal` только ниже сгиба

`.reveal` держит `opacity: 0`, пока `main.js` не добавит `is-in`. LCP-узел внутри `.reveal` невидим до загрузки и выполнения JS (K1). Кейс: `elementRenderDelay` 4–5.7 с на контактах, блоге, портфолио, посте. Правило: блоки `above_fold` и узел `lcp` из `pages-map` — без `.reveal` (H1 и обёртка, CTA под ним, обложка поста, первая карточка / плитка, блок контактов первого экрана). Проверки: `lint:prototype` (прототип), `perf-markup` (WordPress).

## 4. LCP-картинки и `lazy`

- **Ровно одна** картинка страницы — `loading="eager" fetchpriority="high"` (`starter_image( …, [ 'priority' => true ] )`): та, что реально LCP (`lcp.kind: image`). Остальные — `lazy` + `async`.
- **Ловушка WP** (K3): ядро само вешает `fetchpriority="high"` на первую «большую» картинку без явного `loading` — картинка под сгибом отнимет канал у LCP. `starter_image()` всегда ставит `loading`.
- Всегда `width`/`height` или `aspect-ratio` у контейнера. Кейс: галерея без `loading` и размеров — mobile LCP 5.0 с и desktop CLS 0.46; после — 1.8 с и 0.
- Где hero без картинки, LCP — текст (H1 / лид): его скорость определяют шрифты, CSS и скрипты, не картинки.
- `preload` обложки не нужен: картинка находится в HTML сразу.

## 5. Сторонние скрипты: GA4

`gtag.js` (~170 КБ) не в критическом пути: заглушка `dataLayer` в HTML, загрузка через `delayMs` после `load` или при первом взаимодействии — [`analytics.md`](analytics.md). Кейс: до этого TBT ~130 мс и регресс каталога 100 → 92 из-за gtag в окне измерения. Прогоны PSI с GA4 и без несравнимы — фиксировать on/off (K7).

## 6. Фасады встраиваний

Живой iframe карты: 300–700 КБ, ~250 мс main-thread, ошибки консоли (кейс: TBT до 350 мс, Best Practices 96). Решение — `template-parts/embed-facade.php`: лёгкая заглушка с `aspect-ratio`, iframe из `data-src` только по клику, ссылка «открыть у провайдера». Тот же паттерн — видео, виджеты чатов.

## 7. Остатки прототипа

Скрипт прототипа делал `fetch('data/company.json')` — в WordPress 404 и ошибка консоли (минус Best Practices) (K9). Данные — из разметки или `window.STARTER_*`; `check:naming` (`prototype-data-fetch`) и e2e `console` ловят регресс. После переноса каждой страницы — консоль и Network без 404.

## 8. Изображения и WebP

Размер карточки из конфига вместо `full`, `sizes` у каждого вывода; WebP-подразмеры q80 без изменения оригиналов (K11); srcset без оригиналов; регенерация старых вложений — отдельная процедура с бэкапом ([`contracts/images.md`](../contracts/images.md)). Кейс: PNG −55 %, фото −15–20 %; srcset с 1536w/2048w оригиналами тянул до 1 МБ на hi-DPI. Сознательно не делается: `max_srcset_image_width` (портит лайтбокс), WebP-копия маленькой JPG-заглушки (выигрыш ничтожен).

## Чеклист блока / страницы

- [ ] LCP-кандидат определён и записан в `pages-map` (`lcp`, `above_fold`); он не в `.reveal`.
- [ ] Одна LCP-картинка `priority`, остальные `lazy`; у всех `width`/`height`.
- [ ] Картинки из Media Library, размер карточки / `large` с `sizes`, не `full`.
- [ ] Новый скрипт — `starter_script_args()`, зависимости проверены по HTML.
- [ ] Нет новых внешних origin в критическом пути; тяжёлое — за кликом (`embed-facade`).
- [ ] Новые шрифты / веса: подмножества, измеренный fallback, preload только критичных.
- [ ] Консоль и Network без 404 и ошибок.
- [ ] `npm run gate:page -- <url>` зелёный; PSI — только по явной просьбе после деплоя.

## Не делать

- `.reveal` на H1, CTA, обложке, первой карточке / плитке.
- Скрипт без `strategy`; зависимый без `strategy` к отложенному.
- `gtag.js` через `<script src>` в HTML; живой iframe карты / видео при загрузке.
- Preload всей семьи шрифтов; шрифты с CDN; `.woff` как основной формат; метрики fallback «на глаз».
- `fetchpriority="high"` на картинках не из LCP.
- Оптимизировать то, что PSI не назвал (контраст при A11y ≥ 90, «unused JS» темы, критический CSS ради 100 мс).

## Вне кода темы

Хостинг: page cache, `Cache-Control` для HTML, `immutable` для assets / uploads, регенерация WebP (K15) — пункты [`launch.md`](launch.md). Кейс: без page cache серверный отклик из региона аудитории 0.6–0.8 с при TTFB в PSI 2–4 мс.
